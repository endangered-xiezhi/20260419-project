# 飞书多维表格接入与三会治理系统实施方案

更新日期：2026-07-14

## 1. 结论

现有项目适合作为产品原型继续使用，前端技术栈不必推倒重来；但当前架构不能直接作为生产系统接入飞书多维表格。

建议采用以下目标架构：

> React 前端负责交互；Node/Express 服务负责飞书 OAuth、凭证保管、字段转换、合规校验和文书生成；飞书多维表格保存业务主数据；飞书云空间保存模板和归档文件；另设一个很小的安全存储保存会话、刷新令牌、任务幂等键和审计信息。

对于目前“单家公司内部使用”的场景，推荐采用双身份方案：

- 用户通过飞书 OAuth 授权码登录，系统识别操作者并保留审计轨迹。
- 后台批处理和文书生成使用企业自建应用的 `tenant_access_token`，避免任务因某位用户的令牌过期而中断。
- 飞书应用必须被添加为目标 Base 的协作者；否则即使取得 token，也不能访问该 Base。

如果以后做成面向多家公司的 SaaS，再把后台身份切换为各租户安装后的 tenant 身份，并增加租户隔离。

## 2. `.base` 文件评估

`会议合规管理系统-2.base` 是飞书多维表格离线包，不是授权码，也不能直接作为 API 凭证使用。文件可以导入飞书后形成一个在线 Base；真正接入时，应读取导入后在线 Base 的 URL，并通过 API 获取实际的 `app_token`、`table_id` 和 `field_id`。

离线包中已经包含 12 张业务表：

1. 会议表
2. 议案表
3. 人员表
4. 股东表
5. 表决表
6. 风险表
7. 法规索引表
8. 待办表
9. 文书模板表
10. 文书表
11. 会议类型分类表
12. 会议批次表

同时包含 3 个自动化流程，其中 2 个启用、1 个停用。启用流程已经涉及记录变化、AI 生成文本、生成文档、飞书消息和创建任务，说明业务思路已经比较完整。

### 做得合理的部分

- 会议、议案、人员、表决、风险、文书之间已经使用关联字段建立关系。
- 风险与待办分离，便于形成整改闭环。
- 文书模板与生成文书分离，具备模板复用和版本化的基础。
- 会议批次和会议类型分类可以支持董事会、监事会、股东会分组归档。
- 多维表格适合承载当前体量的结构化业务数据和人工协作。

### 上线前必须调整的部分

1. 人员表的“姓名”目前是飞书用户字段。外部董事、自然人股东、法人股东代表未必属于本企业飞书，应拆成“姓名（文本）”和“飞书账号（用户，可空）”。
2. “任期起止”只有一个日期字段，应拆成“任期开始日”和“任期结束日”。
3. 文书模板表的“是否启用”是文本字段，应改为复选框；还应增加“模板文件”“模板版本”“生效日期”“内容哈希”。
4. 会议表缺少公司主体、会议地点、召开方式、通知发出时间、通知期限依据、应到人数、实到人数、法定人数校验结果等合规关键字段。
5. 表决表缺少表决权数/股份数、同意权数、反对权数、弃权权数、回避权数和通过门槛，无法稳定计算决议是否通过。
6. 风险表的“法律依据”是普通文本，建议改为关联法规索引，同时保留引用条款文本快照，避免法规更新后历史记录失真。
7. 文书表不应把完整正式文书只存为长文本。应保存云文档/文件链接、模板版本、数据快照、文件哈希、生成状态、审核状态和签署状态。
8. 缺少“生成任务”和“审计日志”。没有这两类数据时，重复点击、API 重试或自动化重复触发可能生成多份文书，且难以追查是谁在何时改了什么。
9. 离线包内的 ID 只可用于分析，不应硬编码到代码。导入或复制 Base 后，系统应重新发现并保存在线资源 ID。

建议新增 4 张表：

- 公司主体表：公司名称、统一社会信用代码、章程版本、治理结构、默认归档目录。
- 会议通知与送达表：收件人、送达方式、发送时间、回执、是否满足期限。
- 文书生成任务表：任务键、会议、模板版本、状态、错误、重试次数、生成文件。
- 审计/归档表：操作者、动作、前后数据摘要、文件哈希、归档目录、归档时间。

## 3. 现有代码框架评估

### 可以保留

- React 19 + TypeScript + Vite 适合当前管理后台。
- Tailwind 和现有企业治理视觉风格可以继续使用。
- 仪表盘、会议管理、录音纪要、合规审查、文书中心、人员矩阵的产品分区合理。
- Express 服务可以作为第一阶段的 API 中间层，不必立即更换语言或框架。
- 现有 XML/Word 生成代码可保留作为原型和字段映射参考。

### 需要重构

- 业务数据目前分散在至少 19 个 `localStorage` 键中，同一类文书还存在不同键名；这会产生页面间数据不一致，且无法多人协作。
- 系统设置把外部 API Key 存入浏览器，生产环境不可接受。所有密钥和刷新令牌必须只保存在服务端。
- `DocumentCenter.tsx` 约 3,763 行，`MeetingManager.tsx` 约 1,513 行，`ComplianceReview.tsx` 约 1,007 行；应按页面、表单、数据访问和领域服务拆分。
- `server.ts` 同时承担开发服务器、上传、语音、AI 代理等职责，应拆成路由、服务、飞书客户端和任务处理器。
- 当前 TypeScript 检查有 43 处错误，包括路径别名、接口类型、缺失函数和组件参数不一致。必须先建立可通过的质量基线。
- 当前没有自动化测试，也没有真正的登录、会话、权限控制、CSRF 防护、速率限制和审计日志。
- 当前文书生成主要在浏览器中完成。正式文书应在服务端生成，以保证模板一致、可重试、可审计和不受浏览器关闭影响。

整体判断：产品结构约 7/10，原型技术选型约 7/10，生产可用性约 3/10。正确做法是保留界面与业务成果，逐层替换数据和服务基础设施。

## 4. 授权码连接方案

### 4.1 用户看到的流程

1. 用户在“系统设置 → 飞书连接”点击“连接飞书”。
2. 前端打开后端地址 `GET /api/auth/feishu/start`。
3. 后端生成一次性 `state`，写入安全会话，然后重定向至飞书授权页。
4. 用户同意后，飞书把浏览器重定向到 `GET /api/auth/feishu/callback?code=...&state=...`。
5. 后端校验 `state`，用一次性 code 换取 `user_access_token` 和 `refresh_token`。
6. 后端加密保存 refresh token，浏览器只收到本系统的 HttpOnly 会话 Cookie，不接触飞书 token。
7. 用户粘贴在线 Base 链接，后端验证权限、列出数据表和字段，并显示“连接成功/结构不兼容”。

飞书当前网页授权入口为：

`https://accounts.feishu.cn/open-apis/authen/v1/authorize`

授权码换 token 的服务端接口为：

`POST https://open.feishu.cn/open-apis/authen/v2/oauth/token`

授权码有效期很短且只能使用一次，必须由回调接口立即兑换。若需要长期访问，应申请 `offline_access`，并在每次刷新后原子地保存新的 refresh token，因为旧 refresh token 会立即失效。

### 4.2 推荐的后端接口

```text
GET    /api/auth/feishu/start
GET    /api/auth/feishu/callback
POST   /api/auth/logout
GET    /api/auth/session

POST   /api/integrations/feishu/base/verify
GET    /api/integrations/feishu/base/schema
POST   /api/integrations/feishu/base/mapping

GET    /api/meetings
POST   /api/meetings
GET    /api/meetings/:id
PATCH  /api/meetings/:id
POST   /api/meetings/:id/validate
POST   /api/meetings/:id/documents/generate
GET    /api/jobs/:jobId
POST   /api/meetings/:id/archive
```

### 4.3 凭证与安全边界

以下内容只能存在服务端环境或加密存储中：

- `FEISHU_APP_ID`
- `FEISHU_APP_SECRET`
- `user_access_token`
- `refresh_token`
- token 到期时间
- 会话签名密钥和数据加密密钥

Base 仍然是业务主数据存储，但不能用来保存上述密钥。生产环境至少需要一个小型 PostgreSQL；单机试运行可以先用 SQLite。该存储只保存身份、连接、任务和幂等信息，不取代 Base 的业务数据地位。

## 5. 数据访问与同步设计

前端组件不得直接调用飞书 OpenAPI。所有页面调用本系统 API，后端再调用飞书：

```text
页面表单
  → 本系统 API（校验权限与业务规则）
  → BaseRepository（领域对象与飞书字段互转）
  → FeishuClient（token、重试、限流、日志）
  → 飞书多维表格
```

服务端建议拆分为：

```text
server/
  auth/             OAuth、会话、token 刷新
  feishu/           OpenAPI 客户端、错误映射、限流
  repositories/     meetings、people、proposals、votes、documents
  services/         合规校验、文书生成、归档
  jobs/             异步任务、重试、幂等
  routes/           对前端提供的 API
  security/         加密、权限、审计
```

第一次连接在线 Base 时：

1. 根据用户提交的 Base URL 解析资源 token。
2. 调用“获取 Base 元数据”“列出数据表”“列出字段”。
3. 用表名和字段名进行一次性匹配，显示差异。
4. 用户确认后保存真实的 `app_token/table_id/field_id` 映射。
5. 此后读写使用 ID，不依赖可被用户修改的显示名称。
6. 每次启动或发布前运行 schema check；发现字段被删除或改型时停止写入并报警。

读操作可以并行和缓存；同一张表的写操作应进入串行队列。所有创建操作携带本系统生成的幂等键，避免网络重试造成重复记录。

## 6. 文书生成与归档方案

文书生成不能完全交给大模型。正确分工是：

- 确定性字段：公司名、会议时间、参会人、表决结果、编号、法条引用，由结构化数据直接填充。
- 合规计算：通知期限、法定人数、回避、表决门槛，由规则引擎计算。
- 叙述性内容：会议讨论摘要、风险说明，可由 AI 起草，但必须保留来源纪要并进入人工审核。
- 最终格式：由固定版本的 DOCX 模板渲染，禁止 AI 自由决定排版。

生成流程：

1. 用户选择会议并点击“生成会议文件包”。
2. 服务端创建唯一生成任务，锁定会议数据快照和模板版本。
3. 校验必填字段、通知期限、人员身份、回避事项和表决完整性。
4. 从飞书云空间下载对应模板；小于 20 MB 的文件可使用普通上传/下载接口，大文件使用分片接口。
5. 以结构化字段替换模板占位符，必要时根据纪要调用 AI 生成叙述段落。
6. 生成 DOCX；需要 PDF 时由服务器统一转换。
7. 将文件上传到“公司/年度/会议类型/会议编号”目录。
8. 回写文书表：链接、模板版本、数据快照哈希、生成时间、生成者、审核状态。
9. 审核通过后生成归档清单和文件哈希；会议数据变更时，不覆盖旧版本，而是生成新版本。

当前前端使用 `docx` 库重新构造文档，适合原型，但难以完整保留用户提供模板的页眉、页脚、分页、编号和复杂表格。正式版本建议改为服务端基于原始 DOCX 模板做占位符替换，并增加模板回归测试。

## 7. 分阶段执行操作

### 阶段 0：冻结基线（1—2 天）

- 备份当前代码和 Base。
- 把 `.base` 导入目标飞书租户，记录在线 Base URL。
- 暂停修改表名和字段类型。
- 修复 43 个 TypeScript 错误，确保类型检查和生产构建通过。
- 建立至少 10 条覆盖董事会、监事会、股东会的脱敏验收数据。

验收标准：代码可稳定构建；Base 表结构有唯一版本清单。

### 阶段 1：飞书应用与授权（2—3 天）

- 在飞书开放平台创建企业自建应用。
- 配置网页应用重定向 URL。
- 按最小权限申请多维表格读写、云空间文件读写、用户身份基础信息和 `offline_access`；需要日历同步时再申请日历权限。
- 发布应用，并把应用添加为 Base 协作者。
- 实现 OAuth start/callback、token 加密保存、刷新和退出。
- 在设置页增加连接状态、当前用户、Base URL、结构检查结果。

验收标准：用户可完成授权；前端看不到 App Secret 或飞书 access token；断开后无法继续访问。

### 阶段 2：Base 数据层（3—5 天）

- 实现 FeishuClient、schema discovery、字段映射和统一错误处理。
- 先接入人员表和会议表，再接议案、表决、风险、文书。
- 建立 Repository 接口，让 UI 不依赖飞书字段格式。
- 将页面数据读取切换为 API；localStorage 仅保留侧栏宽度、筛选条件等个人偏好。
- 增加写入串行、重试、幂等和审计。

验收标准：两名用户在不同浏览器看到同一数据；刷新和换设备不丢失；重复提交不产生重复会议。

### 阶段 3：会议闭环（3—5 天）

- 重构会议创建为分步表单：基础信息 → 人员 → 议案 → 通知与期限 → 合规预检。
- 接入人员任期、独立性、关联关系、回避事项。
- 接入表决权数和通过门槛计算。
- 将风险自动创建为待办，并保留规则版本与证据。

验收标准：三类会议各跑通一条完整流程；关键字段缺失时不能进入下一阶段。

### 阶段 4：标准文书与归档（5—8 天）

- 整理 21 个现有模板，确定首批 MVP：会议通知、议案、议程、签到表、授权委托书、表决票、表决统计、会议记录、决议。
- 为每个模板建立字段字典、必填规则和金样文件。
- 实现服务端生成任务、版本管理、云盘上传和 Base 回写。
- 实现一键生成会议文件包和归档清单。

验收标准：同一数据重复生成内容一致；模板变更可追溯；历史版本不可被覆盖。

### 阶段 5：事件、自动化与上线（3—5 天）

- 保留 Base 自动化做消息提醒和人工协同；核心生成任务由服务端掌控。
- 如需双向实时同步，订阅 Base 记录变更事件；事件只触发刷新/入队，不直接重复生成文书。
- 增加角色权限、操作审计、限流、备份恢复和告警。
- 完成授权失败、token 过期、字段变更、API 限流、生成失败的异常演练。

验收标准：连续试运行一周无重复文书、无数据丢失、无凭证泄露。

## 8. 首个开发迭代建议

第一迭代不要同时改所有页面，建议只交付以下垂直切片：

1. 飞书授权登录。
2. 在线 Base 连接与结构检查。
3. 从人员表读取人员。
4. 创建一场董事会会议并写入会议表。
5. 关联人员和一项议案。
6. 基于一个会议通知 DOCX 模板生成文件、上传云盘并回写文书表。

这个切片跑通后，技术链路已经覆盖授权、读、写、关联、模板、文件和回写，剩余功能可以按同一模式扩展。
